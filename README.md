A NixOS multi-host system flake, a set of Nix expressions that declaratively
configure every machine I use, from the kernel down to the desktop wallpaper.

*Everything is declaratively declared as everything should be :3*

## Commands you should know:

This is a multi-host configuration: the hostname of the current machine selects
which host configuration is applied, so you only need to pass the machine's name.

- Rebuild and switch the system configuration (from the configuration directory):

```
nh os switch -H mayuri
```

OR

```
nh os switch -H kurisu
```

The `programs.nh.flake` option points this repo, so `nh` uses the config from
`/home/anas/nixfiles`.

- Update the flake inputs:

```
nix flake update
```

- Connect to internet (Change what's inside the brackets with your info).

```
iwctl --passphrase [passphrase] station [device] connect [SSID]
```

- Temporally modifying the Firewall rules:

```sh
Open TCP port:
  nixos-firewall-tool open tcp 8888

Open UDP port:
  nixos-firewall-tool open udp 51820

Show all firewall rules:
  nixos-firewall-tool show

Reset firewall configuration to system settings:
  nixos-firewall-tool reset
```

## Multi-host setup

This repository manages several NixOS hosts, each described in its own file
under `hosts/`:

- `hosts/mayuri.nix` — Lenovo Legion Y540 laptop (Mayuri)
- `hosts/kurisu.nix` — Dell Latitude 5420 laptop (Kurisu)

Each host file imports its own `hosts/<host>-hardware-configuration.nix`
(generated by `nixos-generate-config`) and holds host-specific settings such
as networking, GPU and bluetooth. Shared configuration lives in
`configuration.nix`, `cache.nix` / `peer-cache.nix`, `modules/`, `services/`
and `users/`.

### Secrets (`nix-secrets`)

Secrets are managed with
[nix-secrets](https://github.com/unnamed-systems/nix-secrets) and encrypted
with age. The shared module is `modules/nix-secrets.nix`; it is imported by
`modules/default.nix`, so every host gets the same module, but each host only
declares the secrets it actually uses.

Encryption keys and recipient aliases are **host-specific** and live in the
host file:

```nix
# hosts/<host>.nix
nix-secrets = {
  enable = true;
  identityPaths = [ "/home/anas/.nix-secrets/keys.txt" ];
  recipientAliases.anas = "age1..."; # public key from `nix-secrets keygen`
};
```

`nix-secrets.enable` turns activation on for that host. A host without it keeps
the module available but does not decrypt anything.

Secrets are declared by the feature module or host that uses them. For example,
enabling `ovpn-proxy` declares its three OpenVPN secrets on that host only, so a
host that does not use the proxy never tries to decrypt them. Every declared
secret can still be disabled per host:

```nix
nix-secrets.secrets."openvpn/mayuri/config".enable = false;
```

Templates use the same option namespace. Their content is interpolated when
the secrets are activated:

```nix
nix-secrets.templates."example/credentials".content = ''
  ${config.security.nix-secrets.secrets."example/username"}
  ${config.security.nix-secrets.secrets."example/password"}
'';
```

#### Managing secrets

Generate an age key once per host (do not commit the private key):

```sh
mkdir -p ~/.nix-secrets
nix-secrets keygen -o ~/.nix-secrets/keys.txt
```

Put the printed public key into that host's `recipientAliases.anas`, then edit
the encrypted values. `-f` is a global option, so it goes before `edit`.

Each host uses its own secret names, so every encrypted file is only readable
by the host it was encrypted for.

Mayuri:

```sh
nix-secrets -f .#mayuri edit openvpn/mayuri/username
nix-secrets -f .#mayuri edit openvpn/mayuri/password
nix-secrets -f .#mayuri edit openvpn/mayuri/config
```

Kurisu:

```sh
nix-secrets -f .#kurisu edit openvpn/kurisu/username
nix-secrets -f .#kurisu edit openvpn/kurisu/password
nix-secrets -f .#kurisu edit openvpn/kurisu/config
```

The CLI only sees secrets that are enabled on that host. Kurisu declares its
OpenVPN secrets in `nix-secrets.secrets` even while `ovpn-proxy.enable = false`,
so they can be created before the container is enabled. Once all three
encrypted files exist, set `ovpn-proxy.enable = true` and rebuild.

The editor is taken from `$EDITOR`. To pipe a value in instead of opening an
editor (useful for scripted updates), set it to `-`:

```sh
EDITOR=- nix-secrets -f .#mayuri edit openvpn/mayuri/username < username.txt
```

If evaluation fails with:

```text
error: file '/fsmonitor--daemon.ipc' has an unsupported type
```

the flake is being copied as a plain path, which includes a stale
`.git/fsmonitor--daemon.ipc` socket. Use the git URL form of the flake
reference instead:

```sh
nix-secrets -f "git+file://$PWD#mayuri" edit openvpn/mayuri/username
```

The secrets are stored in `secrets/` (`storagePath` is set to
`/home/anas/nixfiles/secrets`) and must be tracked by git so the flake can see
them:

```sh
git add secrets/
```

Then rebuild:

```sh
nh os switch -H mayuri
```

The `nix-secrets` CLI is part of the development shell, and secret names are
host-specific: if a host has `nix-secrets.enable = false`, its manifest has no
secrets and you must edit from a host that has them enabled.

### OpenVPN HTTP proxy (`ovpn-proxy`)

`modules/ovpn-proxy.nix` runs OpenVPN and Privoxy inside a NixOS container and
exposes the proxy on the host's LAN interface. It is imported by
`modules/default.nix`, but nothing runs unless a host enables it:

```nix
# hosts/mayuri.nix
ovpn-proxy = {
  enable = true;
  externalInterface = "enp7s0";
  configSecret = "openvpn/mayuri/config";
  usernameSecret = "openvpn/mayuri/username";
  passwordSecret = "openvpn/mayuri/password";
  credentialsTemplate = "openvpn/mayuri/credentials";

  # MagicDNS resolves the bare name `mayuri` to this Tailscale address.
  extraLoopbackIPs = [ "100.126.74.4" ];
};
```

The LAN address and prefix are read from the first IPv4 address on
`externalInterface` (`192.168.1.2/24` on Mayuri, `192.168.1.3/24` on Kurisu).
That address is used for the host port forward and for the container's return
route to LAN clients. Override `lanAddress` / `lanPrefixLength` if the proxy
should be reached through a different address.

Kurisu points at its own set:

```nix
# hosts/kurisu.nix
ovpn-proxy = {
  enable = true; # after the secrets below exist
  externalInterface = "enp44s0";
  configSecret = "openvpn/kurisu/config";
  usernameSecret = "openvpn/kurisu/username";
  passwordSecret = "openvpn/kurisu/password";
  credentialsTemplate = "openvpn/kurisu/credentials";

  # MagicDNS resolves the bare name `kurisu` to this Tailscale address.
  extraLoopbackIPs = [ "100.98.50.57" ];
};
```

Other per-host options:

| Option                | Default                    | Purpose                                             |
| --------------------- | -------------------------- | --------------------------------------------------- |
| `port`                | `7777`                     | TCP port exposed on the host                        |
| `proxyPort`           | `8080`                     | Privoxy port inside the container                   |
| `hostAddress`         | `10.234.0.1`               | Host side of the private container network          |
| `localAddress`        | `10.234.0.2`               | Container side of the private container network     |
| `network`             | `10.234.0.0/24`            | Container network used for NAT                      |
| `dns`                 | `1.1.1.1`, `1.0.0.1`       | DNS servers inside the container                    |
| `loopbackIPs`         | `127.0.0.1`, `127.0.0.2`, LAN | Addresses allowed to use the forwarded port       |
| `extraLoopbackIPs`    | `[ ]`                      | Extra addresses appended, e.g. a Tailscale address  |
| `openvpnServer`       | `proton`                   | Name of the OpenVPN systemd service                  |
| `configSecret`        | `openvpn/config`           | `.ovpn` configuration secret                        |
| `usernameSecret`      | `openvpn/username`         | OpenVPN username secret                             |
| `passwordSecret`      | `openvpn/password`         | OpenVPN password secret                             |
| `credentialsTemplate` | `openvpn/credentials`      | Rendered username/password template                 |

The container is only created when `enable = true`, `externalInterface` is
set, and all three secrets are enabled. The credentials template is rendered
automatically, so there is no separate `.enc` file for it.

#### Accessing the proxy

From a machine connected to the Tailscale tailnet, the bare hostname resolves
through MagicDNS:

```sh
curl -x http://kurisu:7777 https://ifconfig.me
```

MagicDNS resolves each host to its Tailscale address, so both hosts list their
Tailscale address in `extraLoopbackIPs`. The port forward then works both on
the LAN and over Tailscale.

On the LAN, mDNS works without Tailscale:

```sh
curl -x http://kurisu.local:7777 https://ifconfig.me
```

On the host itself, `127.0.0.2` (the hostname address) is included by default.
If you want bare `kurisu` to resolve to the LAN address without Tailscale, add
`192.168.1.3 kurisu` to the client's `/etc/hosts` or to the local DNS server.

#### Troubleshooting: `Failed to create an input reader`

If a switch fails during nix-secrets activation with:

```text
INFO Nothing to deploy
ERROR Failed to create an input reader
Failed to run activate script
```

the manifest references an `.enc` file that is not present in the flake source.
Flakes only see git-tracked files, so an untracked secret is invisible even
though it exists on disk.

Check that:

1. The secret is declared on that host and `nix-secrets.enable = true`.
2. The file path matches the secret name:
   `openvpn/mayuri/config` → `secrets/openvpn/mayuri/config.enc`.
3. The file is tracked or staged: `git add secrets/` and `git status --short`.
4. Re-run the switch:

   ```sh
   sudo nixos-rebuild switch --flake .#<host>
   ```

If the source secret cannot be read with `nix-secrets decrypt` because the
container is disabled on that host, decrypt it directly with age and pipe it
into the target host:

```sh
nix shell nixpkgs#age -c age --decrypt \
  --identity /home/anas/.nix-secrets/keys.txt \
  --output /tmp/secret \
  secrets/openvpn/mayuri/config.enc

EDITOR=- nix-secrets -f "git+file:///path/to/nixfiles#kurisu" \
  edit openvpn/kurisu/config < /tmp/secret

rm -f /tmp/secret
```

The target host's manifest decides the recipient, so the new file is encrypted
to that host's key.

### Mutual binary cache (`peer-cache.nix`)

`mayuri` and `kurisu` form a mutual binary-cache pair, wired in via
`cache.nix` → `peer-cache.nix`:

- each host serves its whole store over HTTP with **harmonia** on port 5000
  (`http://<peer>.local:5000`, names resolved via mDNS/avahi), signing
  responses with its own key;
- every build is automatically pushed to the peer with a `post-build-hook`
  that runs `nix copy --to ssh-ng://root@<peer>.local`;
- pushes use a dedicated ssh keypair stored in `/etc/nix/` (nothing under any
  `~/.ssh/`), and host keys are pinned in `/etc/nix/peer-cache-known-hosts`;
- a firewall rule opens port `5000` on the LAN interface only (stays dormant
  while `networking.firewall.enable = false`).

#### Setting it up (once per host)

1. Generate the signing keys (run on **both** machines):

```
doas nix-store --generate-binary-cache-key <host>.lan-1 /etc/nix/peer-cache.key /etc/nix/peer-cache.key.pub
```

2. On one machine, generate the shared push keypair and copy it to the other:

```
ssh-keygen -q -t ed25519 -N '' -C peer-cache -f /tmp/peer-cache-push
doas install -m 600 /tmp/peer-cache-push /etc/nix/peer-cache-push.key
cat /tmp/peer-cache-push | ssh root@<peer>.local 'umask 077; cat > /etc/nix/peer-cache-push.key'
```

3. Paste the three public keys into `peer-cache.nix`, replacing the
   placeholders:

   - both signing keys (`cat /etc/nix/peer-cache.key.pub` on each machine) →
     the `trusted-public-keys` list;
   - the push public key (`cat /tmp/peer-cache-push.pub`) → the
     `users.users.root.openssh.authorizedKeys.keys` list.

   The signing keys must exist **before** the first switch, otherwise the
   harmonia unit fails to start (`LoadCredential`).

4. Rebuild both hosts and restart the daemon so the new `post-build-hook`
   is picked up:

```
nh os switch -H <host>
doas systemctl restart nix-daemon
```

#### Verifying

```
# build a path no public cache has, on one host
nix build --impure --expr 'with import <nixpkgs> {}; runCommand "peer-cache-test" {} "echo hello > $out"'
p=$(readlink -f result); h=$(basename "$p" | cut -d- -f1)

# it should be signed and served by the peer's cache
curl -s "http://<peer>.local:5000/$h.narinfo"        # expect Sig: <peer>.lan-1:...

# on the peer: the push already landed; delete it, then fetch it back
nix path-info "$p" && doas nix-store --delete "$p"
nix build --impure --expr '<same expr>' --dry-run --option substituters "http://<host>.local:5000"
```

The pair is strictly two-node: `peer-cache.nix` maps each host to the single
other entry in its `nodes` table. Adding a third host requires extending the
module to push to (and substitute from) every other node.

### How to add a new host

1. Generate the hardware configuration for the machine:

```
nixos-generate-config --root /mnt --show-hardware-config > hosts/<host>-hardware-configuration.nix
```

2. Create `hosts/<host>.nix` importing that hardware config and set the
   host-specific options you need (hostname, networking, GPU, ...). If the host
   should decrypt secrets, also set `nix-secrets.enable`, `identityPaths` and
   `recipientAliases` there.

3. Register the host in `flake.nix` by copying an existing
   `nixosConfigurations` block (e.g. `mayuri`) and renaming it to the new host
   name in both the attribute name and the imported `hosts/<host>.nix`.

4. Join the binary-cache pair: add the host to the `nodes` table in
   `peer-cache.nix` (lowercase hostname + LAN interface name) and follow the
   *Mutual binary cache* setup steps above to generate its signing key and
   paste the public keys. Note the module is currently a strict two-node pair —
   with more hosts it needs extending to push to every other node.

5. Add the host to the `hosts` output (used by the CI workflow to discover and
   build/eval each host), copying an existing entry and setting the right
   `hostPlatform`:

```
hosts.<host> = {
  hostPlatform = "x86_64-linux";
  large = false; # set to true to skip building in CI
};
```

6. Optionally expose the host as a package so it can be built directly. Inside
   the `packages = forEachSupportedSystem (...)` block, add:

```
<host> = self.nixosConfigurations.<host>.config.system.build.toplevel;
```

   which resolves to `packages.<system>.<host>` (e.g. `packages.x86_64-linux.mayuri`).

7. Switch to it:

```
nh os switch -H <host>
```

## Nix registry

`registry.nix` keeps the `nix registry` in sync with this flake's inputs, so
commands like `nix shell`, `nix run` and `nix develop` resolve to the exact
revisions pinned in `flake.lock` automatically:

| Registry alias        | Resolves to                             |
| --------------------- | --------------------------------------- |
| `nixpkgs`             | `nixos-26.05` channel (stable)          |
| `nixpkgs-unstable`    | `nixos-unstable` channel                |
| `nur`                 | anas NUR                            |
| `home-manager`        | home-manager `release-26.05`      |
| `impermanence`        | nix-community/impermanence        |
| `nix-alien`           | thiagokokada/nix-alien            |
| `lqth`                | 0x61nas/lqth                      |
| `archy-dwm`           | archy-linux/archy-dwm             |
| `nix-jetbrains-plugins` | nix-community/nix-jetbrains-plugins |

Try it out in a shell:

```
nix shell nixpkgs#ripgrep
nix shell nixpkgs-unstable#btop
nix run nixpkgs#fzf
```

You can mix stable and unstable packages in one shell:

```
nix shell nixpkgs#git nixpkgs-unstable#neovim
```

To add more registries, add the input to `flake.nix` and an entry to
`registry.nix`; delete `nix.registry.<name>` to drop an entry.

## Installation

I'll guide you through the Installation, but first make sure to download the Minimal ISO image available at [NixOS](https://nixos.org/download#nixos-iso) and make a bootable drive with it.
and an ethernet cable to make things easier. We shall begin!

> Only follow these steps after using the bootable drive, changing BIOS boot priority and getting into the installation!

### Pre-install (drive preparation)

```sh
video=1920x1080
setfont ter-128n
# configure networking as needed (skip this if you're using ethernet)
sudo -i
lsblk # check info about partitions and the device you want to use for the installation
gdisk /dev/vda #change according to your system, for me it's /dev/nvme0n1
# then configure 600M type ef00, rest ext4 type 8300 as described below
# Type "n" to make a new partition, choose the partition number, first sector can be default but last sector should be 600M. Hex code for EFI is ef00.
# Now type n again to make another partition, this time we'll leave everything as default. After finishing these steps, make sure to write it to the disk by typing "w".
lsblk
mkfs.fat -F 32 -n boot /dev/vda1
mkfs.ext4 -L nixos /dev/vda2
mount /dev/disk/by-label/nixos /mnt
mkdir /mnt/boot
mount /dev/disk/by-label/boot /mnt/boot
```
### The actual installation

After mounting the partitions, you can move to the second part...

```sh
# go inside a nix shell with the specified programs
nix-shell -p git nixUnstable neovim
# create this folder if necessary
mkdir -p /mnt/etc/
# clone the repo
git clone https://github.com/anas/nixfiles.git /mnt/etc/nixos --recurse-submodules
# generate the config and take some files
nixos-generate-config --root /mnt --show-hardware-config > /mnt/etc/nixos/hosts/mayuri-hardware-configuration.nix
# make sure you're in this path
cd /mnt/etc/nixos
# Install my config:
nixos-install --flake '.#mayuri'
```
